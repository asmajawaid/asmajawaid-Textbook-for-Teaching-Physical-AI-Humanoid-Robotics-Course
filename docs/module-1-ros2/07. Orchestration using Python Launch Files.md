# Orchestration using Python Launch Files

## 7.1. The Complexity of Multi-Process Systems

In the initial stages of robotic development, engineers typically execute nodes manually via the command-line interface (CLI). A developer might open a terminal to start a sensor driver, a second terminal for a perception algorithm, and a third for a control loop. While sufficient for prototyping, this manual approach becomes untenable as system complexity scales. A functional autonomous robot often comprises dozens or hundreds of distinct processes (nodes) that must be initialized in a specific order, with precise configuration parameters, and continuously monitored for failure.

To address this, ROS 2 provides the **Launch System**. Unlike simple shell scripts that execute commands sequentially, the Launch System is a sophisticated orchestration engine designed to manage the lifecycle of multiple networked processes. It handles process invocation, configuration injection, event handling, and termination logic within a unified framework.

## 7.2. The Evolution to Python-Based Configuration

Historically, ROS 1 utilized XML-based launch files. While declarative and easy to parse, XML lacked the expressiveness required for complex conditional logic (e.g., "if the camera is USB-based, start Node A; otherwise, start Node B").

ROS 2 transitions the Launch System to **Python**. By defining the system configuration in a general-purpose programming language, architects gain access to the full power of algorithmic logic, standard libraries (such as `os` and `sys`), and third-party modules. This shift transforms the launch file from a static configuration artifact into a dynamic generator that constructs the system state description programmatically at runtime.

## 7.3. The Launch Description Entity

The fundamental unit of the Launch System is the **Launch Description**. This is not a script that executes imperatively from top to bottom; rather, it is a declarative data structure returned by the entry point function of the file.

The Launch Description is a collection of **Actions**. An Action represents an intention to perform a task. The Launch Service iterates through this collection and executes the valid actions. Key action primitives include:
*   **Node Actions:** The instruction to execute a ROS 2 binary. This encapsulates the package name, executable name, namespace, remapping rules, and parameter files.
*   **Include Actions:** The instruction to parse and include another launch file. This allows for modular system design, where a "top-level" launch file aggregates smaller, component-specific launch files (e.g., `navigation.launch.py` includes `lidar.launch.py` and `planner.launch.py`).
*   **ExecuteProcess Actions:** The instruction to run an arbitrary shell command that is not necessarily a ROS node (e.g., opening a visualization tool or recording a bag file).

## 7.4. Dynamic Resolution via Substitutions

A challenge in defining launch files is that file paths and system configurations differ across machines. Hardcoding a path like `/home/user/robot/config.yaml` destroys portability. To solve this, the Launch System employs **Substitutions**.

Substitutions are variables that are not resolved at the time the Python script is parsed, but rather at the exact moment the Launch Service executes the action. This "lazy evaluation" allows the system to remain flexible.
*   **Package Location Substitutions:** Dynamically resolving the install directory of a package (e.g., finding where `my_robot_package` is installed on the current system).
*   **Launch Configuration Substitutions:** Accessing arguments passed to the launch command itself (e.g., `ros2 launch my_pkg run.launch.py mode:=debug`).
*   **Python Expression Substitutions:** Evaluating a Python string expression during the launch process to determine a value dynamically.

## 7.5. Event-Driven Orchestration

Beyond simple process starting, the ROS 2 Launch System is **event-driven**. It can listen for specific state changes in the system and trigger handlers in response. This capability allows for robust fault tolerance and sequential logic:

1.  **Lifecycle Management:** The system can monitor the exit code of a process. If a critical node (like the Odometry Publisher) crashes, an event handler can automatically **Respawn** it after a set delay.
2.  **State Transition Handling:** In the context of Lifecycle Nodes (Managed Nodes), the launch system can trigger transitions (e.g., creating a "Configure" transition only after the node has reached the "Unconfigured" state).
3.  **Sequential Startup:** Using event handlers, an architect can enforce dependencies, such as ensuring that the "Mapping Node" does not launch until the "Lidar Driver" has successfully published its first message or entered an active state.

## 7.6. Argument Declaration and Propagation

To maximize reusability, launch files expose **Launch Arguments**. These act similarly to function parameters in programming. A launch file declares arguments (e.g., `background_color`, `use_simulation`), optionally providing default values.

When a top-level launch file includes a sub-launch file, it can pass values to these arguments. This propagation mechanism allows a single generic launch file to be reused in multiple contexts—for instance, a generic "Laser Scan Matcher" launch file can be invoked twice by a parent file, once configured for the front laser and once for the rear, simply by passing different argument values.

## 7.7. Architectural Suitability

The Launch System is the standard entry point for all production ROS 2 systems.

**Appropriate Use Cases:**
*   **System Startup:** Initializing the entire robot software stack.
*   **Multi-Robot Simulation:** Spawning multiple robot instances with distinct namespaces in a simulator.
*   **Parameter Injection:** Loading complex YAML configurations into nodes at runtime.

**Inappropriate Use Cases:**
*   **Real-Time Logic:** Launch files construct the system graph; they do not run inside the control loop. Do not use launch files to implement robot behavior.
*   **Binary Compilation:** The launch system runs existing executables; it does not compile code. That is the domain of the build system (Colcon).

## 7.8. Implementation Examples

### Example 1: Parameterized Node Launch with Substitutions

**Problem Statement**
We need to launch a LIDAR driver node. The serial port path (`/dev/ttyUSB0` vs `/dev/ttyUSB1`) varies depending on how the hardware is plugged in. We must create a launch file that accepts this path as a command-line argument, using **Substitutions** to inject the value into the node's parameters at runtime.

**Execution Context**
*   **File:** `lidar_driver.launch.py`
*   **Runtime:** `ros2 launch my_pkg lidar_driver.launch.py serial_port:=/dev/ttyUSB1`

**Code Block**

```python
from launch import LaunchDescription
from launch.actions import DeclareLaunchArgument
from launch.substitutions import LaunchConfiguration
from launch_ros.actions import Node

def generate_launch_description():
    # 1. Argument Declaration (Section 7.6)
    # Defines 'serial_port' as a valid CLI argument with a default fallback.
    arg_port = DeclareLaunchArgument(
        'serial_port',
        default_value='/dev/ttyUSB0',
        description='The device path for the LIDAR sensor'
    )

    # 2. Substitution Definition (Section 7.4)
    # Creates a "lazy" variable. It does not hold a string yet;
    # it will resolve to the string value when the action executes.
    port_config = LaunchConfiguration('serial_port')

    # 3. Node Action (Section 7.3)
    lidar_node = Node(
        package='rplidar_ros',
        executable='rplidar_node',
        name='rplidar',
        parameters=[{
            'serial_port': port_config,  # Injecting the substitution
            'frame_id': 'laser_frame',
            'angle_compensate': True
        }],
        output='screen'
    )

    # Returns the declarative description
    return LaunchDescription([
        arg_port,
        lidar_node
    ])
```

**Explanation**
*   **`DeclareLaunchArgument`**: Registers the interface. If the user runs `ros2 launch ... --show-args`, this argument and its description will appear.
*   **`LaunchConfiguration`**: This is the Substitution object. It bridges the gap between the argument provided by the user and the parameter expected by the node.
*   **Lazy Evaluation**: The `parameters` dictionary does not receive a string literal; it receives the substitution object, which the Launch Service resolves immediately before starting the process.

**Dependencies**
*   Requires `launch` and `launch_ros` Python packages (standard in ROS 2).
*   Assumes `rplidar_ros` package is installed.

### Example 2: Composition and Fault Tolerance

**Problem Statement**
A "System Bringup" launch file needs to orchestrate a complex startup. It must:
1.  Include a separate launch file that handles the robot's physical description (URDF).
2.  Launch a navigation controller node.
3.  **Event Handling:** Ensure that if the navigation controller crashes (e.g., due to a memory error), the system automatically restarts it (Respawn) to maintain autonomy.

**Execution Context**
*   **File:** `system_bringup.launch.py`
*   **Runtime:** Standard ROS 2 launch command.

**Code Block**

```python
import os
from ament_index_python.packages import get_package_share_directory
from launch import LaunchDescription
from launch.actions import IncludeLaunchDescription
from launch.launch_description_sources import PythonLaunchDescriptionSource
from launch_ros.actions import Node

def generate_launch_description():
    # Resolve the path dynamically
    description_pkg_dir = get_package_share_directory('robot_description_pkg')

    # 1. Include Action (Section 7.3 & 7.6)
    # Parses and executes another launch file, passing an argument to it.
    urdf_launch = IncludeLaunchDescription(
        PythonLaunchDescriptionSource(
            os.path.join(description_pkg_dir, 'launch', 'urdf.launch.py')
        ),
        launch_arguments={'use_sim_time': 'false'}.items()
    )

    # 2. Event-Driven Node Action (Section 7.5)
    # The 'respawn' flag creates an internal event handler that monitors
    # the process exit code.
    nav_controller_node = Node(
        package='nav2_controller',
        executable='controller_server',
        output='screen',
        parameters=[{'autostart': True}],
        # Fault Tolerance Configuration
        respawn=True,
        respawn_delay=2.0
    )

    return LaunchDescription([
        urdf_launch,
        nav_controller_node
    ])
```

**Explanation**
*   **`IncludeLaunchDescription`**: Demonstrates the compositional architecture. The bringup file delegates the URDF loading to a specialized file, preventing monolithic script growth.
*   **`respawn=True`**: This abstract parameter configures an event handler within the Launch Service. It listens for the process termination event; if the exit code is non-zero (crash), it triggers a timer to re-execute the Node Action after 2.0 seconds.

**Dependencies**
*   Requires `ament_index_python` to locate installed packages.
*   Assumes `nav2_controller` is installed.
