## 3. Topics: Asynchronous Pub/Sub Communication

The dominant communication pattern in distributed robotics is **Publish-Subscribe** (Pub/Sub). This pattern provides a mechanism for asynchronous, many-to-many communication between spatially decoupled processes. In ROS 2, this abstraction is realized through **Topics**. Topics represent named channels over which nodes exchange data streams, functioning as the "bus" of the robotic nervous system.

### 3.1 Architectural Decoupling

In a tightly coupled system, a data producer (e.g., a camera driver) must possess specific knowledge about the data consumer (e.g., a computer vision algorithm), including its network address and port. This creates a brittle dependency graph where adding a new consumer requires modifying the producer.

The Topic architecture resolves this by enforcing **logical and spatial decoupling**:
*   **Logical Decoupling:** Nodes communicate via anonymous interfaces. A publisher generates data without knowledge of who, if anyone, is listening. Conversely, a subscriber consumes data without needing to know the source.
*   **Spatial Decoupling:** The underlying middleware (DDS) handles discovery. Nodes do not need to know the IP addresses or ports of their peers; they simply agree on a Topic Name (e.g., `/camera/image_raw`).

This architecture facilitates high modularity. A logging node, a visualization tool, and a control algorithm can all subscribe to the same sensor topic simultaneously without affecting the performance or logic of the driver node.

### 3.2 The Topic Abstraction

A Topic is a strongly typed, named data bus.

*   **Asynchronous Nature:** Communication is "fire-and-forget." The publisher transmits a message onto the network and immediately resumes execution. It does not wait for an acknowledgment from the subscriber(s), nor does it block until the message is processed.
*   **Multiplicity:** A single topic can have zero, one, or multiple publishers and zero, one, or multiple subscribers (N:M communication).
*   **Continuous Streams:** Topics are optimized for streaming data—continuous updates of state such as sensor readings, robot odometry, or transforms—where the most recent data point often supersedes older ones.

### 3.3 Message Definition and Type Safety

ROS 2 enforces strict type safety across the network using an **Interface Definition Language (IDL)**. Messages are not arbitrary binary blobs; they are structured data objects defined in `.msg` files.

These definitions serve as a contract between distributed components. For two nodes to communicate on a topic, they must not only agree on the topic name but also communicate using the exact same message type. This ensures that the binary serialization of the data (the conversion of in-memory objects to a byte stream for transport) can be correctly deserialized (reconstructed) by the receiving node.

Standard ROS 2 message types include:
*   **Primitive types:** `int32`, `float64`, `bool`, `string`.
*   **Arrays:** Fixed-length (e.g., `float32[3]`) or variable-length (e.g., `uint8[]`).
*   **Composition:** Messages can nest other messages (e.g., a `Pose` message containing `Point` and `Quaternion` messages).

### 3.4 Quality of Service (QoS) Policies

In a real-world robotic network, network conditions vary. A robot might communicate internally over a gigabit Ethernet connection (low latency, zero packet loss) while simultaneously transmitting telemetry to a ground station over high-latency, lossy WiFi. ROS 2 allows developers to tune the behavior of the communication stream via **Quality of Service (QoS)** policies.

While DDS offers extensive QoS configurations, ROS 2 exposes a subset of critical policies for Topics:

#### 3.4.1 Reliability
This policy dictates the guarantee of message delivery.
*   **Reliable:** The middleware guarantees delivery. If a packet is lost during transport, the protocol will attempt retransmission. This is analogous to TCP and is essential for critical data where every message matters (e.g., system configuration changes).
*   **Best Effort:** The middleware attempts to send the data but provides no guarantees. If a packet is dropped, it is lost forever. This is analogous to UDP and is preferred for high-frequency sensor data (e.g., 30Hz LiDAR scans) where acting on the newest data is more important than recovering old, stale data.

#### 3.4.2 History and Depth
This policy manages the message queue on both the publishing and subscribing sides.
*   **Keep Last:** The system maintains a fixed-size buffer (defined by the **Depth** parameter). If new messages arrive faster than the subscriber can process them (or faster than the network can transmit them), the oldest messages in the queue are overwritten.
*   **Keep All:** The system attempts to store every message indefinitely until it is processed. This can lead to unbounded memory growth if the consumer is slower than the producer.

For a connection to be established between a publisher and a subscriber, their QoS policies must be **compatible**. For example, a "Reliable" subscriber cannot request data from a "Best Effort" publisher, as the publisher cannot satisfy the reliability guarantee.

### 3.5 The Subscription Lifecycle

The processing of topic data on the subscriber side is event-driven.
1.  **Registration:** The node registers a **Subscription** with the ROS 2 executor, specifying the topic name, message type, QoS profile, and a callback function.
2.  **Transport:** When a message arrives via the network, the middleware deserializes the byte stream into a language-specific object (e.g., a Python class instance).
3.  **Queueing:** The object is placed in the subscriber's message queue.
4.  **Dispatch:** The Executor identifies that data is available and invokes the registered **Callback Function**, passing the message object as an argument.
5.  **Execution:** The user logic inside the callback executes. This blocks the specific thread assigned by the Executor until completion.

#### Example 1: Implementing a Sensor Publisher with QoS
**Problem Statement:**
Implement a node that simulates a high-frequency LiDAR sensor. Because the data is generated at 30Hz and older scans are irrelevant for real-time obstacle avoidance, the node must use a "Best Effort" QoS profile to minimize latency and network overhead. This demonstrates **QoS Policies** (3.4) and **Continuous Streams** (3.2).

**Execution Context:**
This code is saved as `lidar_publisher.py` in a simulation package. It runs alongside a consumer node (like the one in Example 2).

```python
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy, HistoryPolicy
from sensor_msgs.msg import LaserScan
import time
import math

class LidarSimNode(Node):
    def __init__(self):
        super().__init__('lidar_simulator')
        
        # 1. Define Quality of Service (QoS) Profile
        # We use Best Effort reliability for sensor data (UDP-like behavior)
        # We only keep the last 5 messages to save memory
        qos_profile = QoSProfile(
            reliability=ReliabilityPolicy.BEST_EFFORT,
            history=HistoryPolicy.KEEP_LAST,
            depth=5
        )

        # 2. Create Publisher with the defined QoS
        self.publisher = self.create_publisher(
            LaserScan, 
            '/scan', 
            qos_profile
        )

        # 3. Timer for 30Hz publishing frequency
        self.timer = self.create_timer(1.0 / 30.0, self.publish_scan)
        self.get_logger().info("Lidar Simulator Started at 30Hz")

    def publish_scan(self):
        # Construct a dummy LaserScan message
        scan = LaserScan()
        scan.header.stamp = self.get_clock().now().to_msg()
        scan.header.frame_id = "base_link"
        scan.angle_min = -math.pi / 2
        scan.angle_max = math.pi / 2
        scan.angle_increment = math.pi / 180.0
        scan.range_min = 0.0
        scan.range_max = 10.0
        # Simulate 180 readings with dummy data
        scan.ranges = [5.0] * 180 

        self.publisher.publish(scan)

def main(args=None):
    rclpy.init(args=args)
    node = LidarSimNode()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

**Key Parts Explained:**
*   `QoSProfile`: Explicitly configures the middleware behavior. `ReliabilityPolicy.BEST_EFFORT` tells DDS not to retry dropped packets, which is crucial for high-bandwidth sensor streams.
*   `create_publisher`: Registers the topic `/scan` with the custom QoS profile. Any subscriber connecting to this must have a compatible QoS (e.g., they cannot ask for `RELIABLE`).
*   `LaserScan`: Uses the standard ROS 2 message type for 2D planar scanners, ensuring interoperability with tools like `RViz` and `Nav2`.

**Dependencies:**
*   `sensor_msgs` package.
*   Assumes a compatible DDS implementation (FastDDS or CycloneDDS) is active.

#### Example 2: The Subscription Lifecycle
**Problem Statement:**
Create a safety monitor node that listens to the LiDAR data. It must process the incoming stream to check for obstacles. This demonstrates the **Subscription Lifecycle** (3.5), including registration, type safety, and the callback mechanism.

**Execution Context:**
This code is saved as `safety_monitor.py`.

```python
import rclpy
from rclpy.node import Node
from rclpy.qos import QoSProfile, ReliabilityPolicy
from sensor_msgs.msg import LaserScan

class SafetyMonitorNode(Node):
    def __init__(self):
        super().__init__('safety_monitor')

        # 1. Matching QoS Profile
        # Subscriber must request BEST_EFFORT to be compatible with the publisher
        qos_profile = QoSProfile(
            reliability=ReliabilityPolicy.BEST_EFFORT,
            depth=10
        )

        # 2. Registration
        # We subscribe to '/scan' and enforce the LaserScan type contract.
        self.subscription = self.create_subscription(
            LaserScan,
            '/scan',
            self.scan_callback,
            qos_profile
        )

    def scan_callback(self, msg: LaserScan):
        """
        4. Dispatch & 5. Execution
        This function is invoked by the Executor whenever a new message arrives.
        """
        # Simple logic: Check for objects closer than 1.0 meter
        min_distance = min(msg.ranges)
        
        if min_distance < 1.0:
            self.get_logger().warn(f"Collision Hazard! Object detected at {min_distance:.2f}m")
        else:
            self.get_logger().info(f"Path clear. Min dist: {min_distance:.2f}m", throttle_duration_sec=2.0)

def main(args=None):
    rclpy.init(args=args)
    node = SafetyMonitorNode()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

**Key Parts Explained:**
*   `create_subscription`: Initiates the discovery process. The middleware looks for publishers on `/scan` with type `sensor_msgs/msg/LaserScan`.
*   `scan_callback(self, msg: LaserScan)`: The event handler. The `msg` argument is already deserialized into a Python object with fields like `.ranges` accessible directly.
*   `throttle_duration_sec`: A logging utility to prevent console flooding while processing high-frequency streams.

**Dependencies:**
*   `sensor_msgs` package.
*   This node must be run in the same ROS_DOMAIN_ID as the publisher to receive data.

## 4. Services: Synchronous Request/Response Patterns

### 4.1. The Remote Procedure Call Paradigm

In the architecture of distributed robotic systems, the continuous flow of data—handled via the Publish-Subscribe pattern described in previous sections—addresses the need for state observation. However, observation alone is insufficient for actuation, computation requests, or system-state manipulation. To fulfill these requirements, ROS 2 implements a **Service** mechanism, which is fundamentally a realization of the **Remote Procedure Call (RPC)** paradigm.

Unlike the "fire-and-forget" nature of Topics, the Service architecture is transactional. It establishes a contract of **synchronous** or **logically coupled** interaction between two specific entities: a **Client** (the requester) and a **Server** (the responder). This pattern is derived from first principles of distributed computing where a process on one node triggers the execution of a subroutine on a distinct, potentially remote node, awaiting a return value before proceeding with dependent logic.

The defining characteristic of this pattern is the strong temporal coupling between the request and the response. While the underlying network transport may operate asynchronously, the application logic treats the interaction as a single, atomic unit of work: the Client generates a demand, the Server processes it, and the transaction is only considered complete upon the delivery of the result.

### 4.2. Client-Server Architecture

The topology of a Service is strictly **many-to-one** regarding the provider.
*   **The Service Server:** A node creates a Service Server to offer a specific capability (e.g., "Compute Inverse Kinematics" or "Reset Odometry"). A single Service Server claims a specific service name within the namespace. It binds to the middleware layer, listening for incoming requests.
*   **The Service Client:** Any number of nodes can instantiate Service Clients to utilize this capability. The Client is responsible for serializing the request data and addressing it to the Server.

This contrasts with Topics, where publishers and subscribers are decoupled and unaware of each other's existence. In the Service pattern, the Client must be aware of the existence of the Server to initiate a transaction. If the Server is offline, the Client cannot perform its function, often resulting in a connection timeout or a pending state.

### 4.3. Interface Definition and Typing

Just as Topics rely on Message definitions (`.msg`), Services rely on Service definitions (`.srv`). The Service interface specification is a strictly typed contract that defines the data structure for the bidirectional exchange. This interface is composed of two distinct data blocks separated by a delimiter:

1.  **The Request Block:** This defines the parameters strictly required by the Server to perform the computation or action. It mimics the input arguments of a standard programming function.
2.  **The Response Block:** This defines the data returned to the Client upon completion. It mimics the return values of a function, often including success flags, computed data, or error messages.

The build system compiles these definitions into language-specific structures (C++ structs or Python classes) that handle the serialization and deserialization (marshalling) of the data across the DDS (Data Distribution Service) wire protocol.

### 4.4. Synchronicity and Concurrency

The term "Synchronous" in the context of ROS 2 Services refers to the logical flow of the transaction, but it introduces significant complexity regarding execution threads.

#### 4.4.1. The Blocking Nature of Requests
In a naïve implementation, a Service call is a **blocking operation**. When the Client sends a request, the execution of that specific thread is suspended. The thread remains in a wait state until the network stack delivers the response from the Server.

This behavior presents a critical architectural hazard in robotics known as **deadlock**. If a node attempts to call a Service within a callback that is responsible for handling the response, or if a single-threaded executor is blocked waiting for a response that requires the same executor to process, the system will halt indefinitely.

#### 4.4.2. Asynchronous Implementation of Synchronous Logic
To mitigate blocking hazards while preserving the request/response logic, modern ROS 2 client libraries employ **Futures** and **Promises**.
*   The Client sends the request and immediately receives a "Future" object—a placeholder representing a value that does not yet exist.
*   The Client's thread is released to continue other processing (such as handling sensor data).
*   When the Server responds, the middleware populates the Future.
*   The Client can check the status of the Future or employ a callback mechanism to handle the result once available.

Despite this asynchronous implementation detail, the interaction remains logically synchronous: the robotic behavior depending on that service cannot proceed until the response is received.

### 4.5. Reliability and Quality of Service

Unlike Topics, which often tolerate data loss (e.g., dropping a video frame in favor of a newer one), Services generally require **Reliable Quality of Service (QoS)**. The semantics of a function call imply that if a call is made, it must be executed, or an error must be raised. A "best effort" service call would be architecturally unsound, as it would lead to nondeterministic system states where a robot is unsure if a command was received or ignored. Therefore, the underlying middleware configures the transport layer to ensure packet delivery, acknowledgment, and ordering for service transactions.

### 4.6. Architectural Suitability

The Service pattern is appropriate for:
*   **Fast, discrete computations:** E.g., querying the validity of a trajectory.
*   **State mutations:** E.g., switching a camera on or off.
*   **Data retrieval:** E.g., asking a map server for a specific sub-region.

The Service pattern is **inappropriate** for:
*   **Long-running behaviors:** If a request takes seconds or minutes to complete (e.g., "Drive to the kitchen"), holding a synchronous connection open is fragile and blocks the calling logic. Such behaviors are better handled by the **Action** interface (discussed in subsequent sections), which adds feedback and cancellation capabilities to the asynchronous RPC model.
*   **Continuous data streaming:** High-frequency state updates should remain on Topics to avoid the request/response overhead.

### 4.7. Implementation Examples

#### Example 1: Service Interface and Server Implementation

**Problem Statement**
A robotic perception system requires a service to toggle a camera stream on or off and set its resolution. This represents a "State Mutation" suitable for the Service pattern. We must define the strictly typed interface and implement a server that handles the request synchronously.

**Execution Context**
*   **File:** `perception_interfaces/srv/SetCameraState.srv` (Service Definition)
*   **File:** `camera_service_node.py` (ROS 2 Node)
*   **Runtime:** Requires `perception_interfaces` package to be built.

**Code Block**

```text
# perception_interfaces/srv/SetCameraState.srv

# Request Block
bool active          # Turn camera on (true) or off (false)
string resolution    # E.g., "1920x1080", "640x480"
---
# Response Block
bool success         # Did the state change succeed?
string message       # Informational status or error description
```

```python
# camera_service_node.py
import rclpy
from rclpy.node import Node
from perception_interfaces.srv import SetCameraState

class CameraServiceNode(Node):
    def __init__(self):
        super().__init__('camera_service_server')
        # Create the service server
        # Service Name: 'set_camera_state'
        # Callback: self.handle_set_state
        self.srv = self.create_service(
            SetCameraState, 
            'set_camera_state', 
            self.handle_set_state
        )
        self.get_logger().info('Camera State Service is ready.')

    def handle_set_state(self, request, response):
        """
        Callback function for processing service requests.
        The middleware triggers this when a client sends a request.
        """
        self.get_logger().info(f'Incoming request: Active={request.active}, Res={request.resolution}')

        # Simulate hardware validation logic
        valid_resolutions = ["640x480", "1280x720", "1920x1080"]
        
        if request.active and request.resolution not in valid_resolutions:
            response.success = False
            response.message = f"Invalid resolution: {request.resolution}"
            self.get_logger().warn(f"Failed to set resolution: {request.resolution}")
        else:
            # Logic to interact with actual hardware would go here
            response.success = True
            state_str = "ON" if request.active else "OFF"
            response.message = f"Camera turned {state_str} at {request.resolution}"
            self.get_logger().info(response.message)

        return response

def main(args=None):
    rclpy.init(args=args)
    node = CameraServiceNode()
    rclpy.spin(node)
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

**Explanation**
*   **Service Definition (.srv):** Defines the contract. The client *must* provide `active` and `resolution`; the server *must* return `success` and `message`.
*   **`create_service`:** Registers the node as a provider for the `set_camera_state` service.
*   **Callback Logic:** The `handle_set_state` method receives the request, performs logic (input validation), populates the response object, and returns it. This transaction is atomic.

#### Example 2: Asynchronous Client Implementation

**Problem Statement**
A central mission control node needs to activate the camera. As discussed in **Section 4.4**, calling a service synchronously (`client.call()`) blocks the execution thread. This example demonstrates the **Future/Promise** pattern to call the service asynchronously, allowing the node to continue other tasks (like processing sensor heartbeats) while waiting for the server.

**Execution Context**
*   **File:** `mission_control_node.py`
*   **Runtime:** Must run while `camera_service_node` is active.

**Code Block**

```python
import rclpy
from rclpy.node import Node
from perception_interfaces.srv import SetCameraState

class MissionControlNode(Node):
    def __init__(self):
        super().__init__('mission_control_client')
        # Create a client for the 'set_camera_state' service
        self.cli = self.create_client(SetCameraState, 'set_camera_state')
        
        # Check if the server is available (essential for robustness)
        while not self.cli.wait_for_service(timeout_sec=1.0):
            self.get_logger().info('Service not available, waiting again...')
        
        self.req = SetCameraState.Request()

    def send_request(self, is_active, resolution):
        """
        Sends an asynchronous request and returns the Future object.
        Does NOT block the thread.
        """
        self.req.active = is_active
        self.req.resolution = resolution
        
        self.get_logger().info('Sending async request...')
        # call_async returns a Future immediately
        return self.cli.call_async(self.req)

def main(args=None):
    rclpy.init(args=args)
    mission_node = MissionControlNode()

    # Initiate the service call
    future = mission_node.send_request(True, "1920x1080")

    # The node spins until the Future is complete. 
    # In a complex system, this would be part of a larger event loop 
    # allowing other callbacks (e.g., timers, subscriptions) to run concurrently.
    rclpy.spin_until_future_complete(mission_node, future)

    # Handling the result after the Future is done
    try:
        response = future.result()
        if response.success:
            mission_node.get_logger().info(f'Success: {response.message}')
        else:
            mission_node.get_logger().error(f'Service Error: {response.message}')
    except Exception as e:
        mission_node.get_logger().error(f'Service call failed: {e}')

    mission_node.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

**Explanation**
*   **`wait_for_service`:** A safety mechanism ensuring the client doesn't attempt to send data into a void.
*   **`call_async`:** The core concept of Section 4.4.2. It sends the request and returns a `Future` immediately, releasing the thread.
*   **`spin_until_future_complete`:** A standard ROS 2 pattern that keeps the node responsive to other events (if any) while checking if the service has responded. This prevents the "deadlock" hazard mentioned in Section 4.4.1.

## 5. Actions: Long-Running Tasks with Feedback

### 5.1. The Necessity of Asynchronous Teleology

In the Service pattern discussed previously, interactions are atomic and logically synchronous: a request is made, and the system waits for a response. This model breaks down when applied to **teleological** behaviors—processes directed toward a specific end goal that require non-trivial duration to complete.

Consider a mobile robot instructed to navigate to a coordinate ten meters away. If implemented as a Service, the calling node (the Client) would send the target coordinates and theoretically hang in a blocked state for the duration of the movement. During this interval:
1.  **Lack of Observability:** The Client receives no information about progress. The robot could be 99% there or stuck at the starting line.
2.  **Inability to Intervene:** If the environment changes (e.g., a dynamic obstacle appears), the Client has no standard mechanism to issue a "Stop" or "Redirect" command because it is waiting for the original function to return.
3.  **Timeout Ambiguity:** Selecting an appropriate timeout duration becomes impossible, as travel time varies dynamically.

To address these limitations, ROS 2 introduces the **Action** architectural pattern. Actions are designed for preemptable, long-running tasks that provide continuous feedback during execution.

### 5.2. The Action Paradigm

The Action pattern is a high-level communication protocol built upon the lower-level primitives of Topics and Services. It formalizes a complex interaction between an **Action Client** and an **Action Server**.

Unlike the binary success/failure of a Service, an Action represents a temporal process with a distinct lifecycle. It introduces three critical capabilities absent in Services:
*   **Feedback:** The Server can periodically publish data regarding the progress of the task (e.g., "Distance to goal: 4.5m") without terminating the task.
*   **Preemption (Cancellation):** The Client retains agency during execution. It can asynchronously signal the Server to abort the current task.
*   **Goal Policy:** The Server determines whether to accept or reject a request based on its current state (e.g., rejecting a movement command because the battery is critical).

### 5.3. Compositional Architecture

From a first-principles perspective, an Action is not a monolithic transport mechanism. It is a composite pattern instantiated by the ROS 2 middleware using three underlying entities for every single Action definition:

1.  **The Goal Service (Client $\rightarrow$ Server):** A synchronous service used to initiate the behavior. The Client sends the goal parameters, and the Server replies strictly with an acceptance or rejection of the goal.
2.  **The Result Service (Client $\rightarrow$ Server):** A synchronous service where the Client requests the final outcome. The Server responds only when the task is effectively terminal (succeeded, aborted, or canceled).
3.  **The Feedback Topic (Server $\rightarrow$ Client):** A publish-subscribe channel where the Server streams progress updates.
4.  **The Status Topic (Server $\rightarrow$ Client):** A publish-subscribe channel broadcasting the current state of all goals being processed by the Server (e.g., EXECUTING, CANCELED).
5.  **The Cancel Service (Client $\rightarrow$ Server):** A control interface allowing the Client to request the termination of a specific goal ID.

This composition allows the system to maintain the reliability of TCP-like services for command and control (Goal/Result/Cancel) while utilizing the efficiency of UDP-like topics for streaming data (Feedback/Status).

### 5.4. Interface Definition

Actions are defined in `.action` files, which extend the interface syntax to three distinct fields, separated by hyphens:

1.  **Goal Definition:** The parameters required to initiate the task (e.g., `TargetPose`).
2.  **Result Definition:** The data returned upon completion (e.g., `TotalTimeElapsed`, `FinalPose`).
3.  **Feedback Definition:** The data sent periodically during execution (e.g., `CurrentVelocity`, `DistanceRemaining`).

The build system generates the necessary Service and Message definitions to support the composite architecture described in Section 5.3.

### 5.5. The Action State Machine

A fundamental property of the ROS 2 Action Server is the **Goal Lifecycle State Machine**. Every goal sent to an Action Server enters a formal state machine that dictates valid transitions.

1.  **Accepted:** The Server has received the goal and agreed to process it.
2.  **Executing:** The physical or computational process is active. Feedback is being generated.
3.  **Canceling:** A client has requested preemption, and the Server is performing cleanup operations to stop safely.
4.  **Terminal States:**
    *   **Succeeded:** The goal was achieved successfully.
    *   **Aborted:** The Server encountered an error during execution and stopped.
    *   **Canceled:** The Server successfully stopped execution in response to a preemption request.

Crucially, the **Server** owns the state machine. A Client can *request* a cancellation, but the Server must transition the state. This is vital for hardware safety; a robot arm cannot simply "stop" instantly if it is carrying significant momentum; it must decelerate (Transition: Executing $\rightarrow$ Canceling $\rightarrow$ Canceled).

### 5.6. Concurrency and Goal Handles

Because Actions are asynchronous, an Action Server may handle multiple goals simultaneously or queue them. To manage this, every request is assigned a unique **Goal ID** (UUID).

The Client library wraps this UUID in a **Goal Handle**. The Goal Handle is the reference object used to track the specific invocation of the action. It is through the Goal Handle that the Client correlates specific feedback messages to specific requests and issues cancel commands for one task without disturbing others.

### 5.7. Architectural Suitability

The Action pattern is the standard for robotic behaviors.

**Appropriate Use Cases:**
*   **Navigation:** "Drive to coordinates $(x, y)$." (Long duration, path deviation feedback needed, must be stoppable if a human walks in front).
*   **Manipulation:** "Pick up object A." (Complex motion planning, risk of failure requires abort states).
*   **Perception:** "Scan the room for QR codes." (Scanning takes time; feedback provides the count of codes found so far).

**Inappropriate Use Cases:**
*   **Instantaneous Triggers:** "Reset Gyroscope." (Use a Service).
*   **High-Frequency Control:** "Set motor voltage." (Use a Topic). Actions introduce significant protocol overhead (multiple service calls and topic publications) and are too heavy for real-time control loops running at >100Hz.

### 5.8. Implementation Examples

#### Example 1: Action Definition and Server Logic

**Problem Statement**
We require a `NavigateToPoint` action. The robot needs to move to a target coordinate. This takes time, so the server must stream the remaining distance (feedback) and report the total duration upon arrival (result). The server must also handle "Cancellation" requests—if the client asks to stop, the robot must safely decelerate before marking the goal as Canceled.

**Execution Context**
*   **File:** `robot_interfaces/action/NavigateToPoint.action`
*   **File:** `nav_action_server.py`
*   **Runtime:** Requires `robot_interfaces` to be built and sourced.

**Code Block**

```text
# robot_interfaces/action/NavigateToPoint.action

# Goal
float32 target_x
float32 target_y
---
# Result
bool success
float32 total_time_seconds
---
# Feedback
float32 distance_remaining
```

```python
import time
import rclpy
from rclpy.action import ActionServer, CancelResponse, GoalResponse
from rclpy.node import Node
from rclpy.callback_groups import ReentrantCallbackGroup
from robot_interfaces.action import NavigateToPoint

class NavigationActionServer(Node):
    def __init__(self):
        super().__init__('nav_action_server')
        
        # ReentrantCallbackGroup allows the execute_callback to run concurrently
        # with cancel_callback or other service calls.
        self._cb_group = ReentrantCallbackGroup()
        
        self._action_server = ActionServer(
            self,
            NavigateToPoint,
            'navigate_to_point',
            execute_callback=self.execute_callback,
            goal_callback=self.goal_callback,
            cancel_callback=self.cancel_callback,
            callback_group=self._cb_group
        )
        self.get_logger().info('Navigation Action Server Started')

    def goal_callback(self, goal_request):
        """Policy: Accept or Reject the goal."""
        self.get_logger().info(f'Received goal request: ({goal_request.target_x}, {goal_request.target_y})')
        # Simple policy: Reject negative coordinates for safety
        if goal_request.target_x < 0 or goal_request.target_y < 0:
            self.get_logger().warn('Rejecting invalid goal')
            return GoalResponse.REJECT
        return GoalResponse.ACCEPT

    def cancel_callback(self, goal_handle):
        """Policy: Can we cancel safely right now?"""
        self.get_logger().info('Received cancel request')
        return CancelResponse.ACCEPT

    def execute_callback(self, goal_handle):
        """Main execution logic for the long-running task."""
        self.get_logger().info('Executing goal...')
        
        feedback_msg = NavigateToPoint.Feedback()
        result = NavigateToPoint.Result()
        
        # Simulate movement loop
        distance = 10.0 # Hypothetical start distance
        start_time = self.get_clock().now()

        for i in range(10):
            # 1. Check for cancellation request
            if goal_handle.is_cancel_requested:
                goal_handle.canceled()
                self.get_logger().info('Goal canceled by client')
                result.success = False
                result.total_time_seconds = (self.get_clock().now() - start_time).nanoseconds / 1e9
                return result

            # 2. Perform work (simulate robot moving closer)  
            distance -= 1.0
            time.sleep(1.0) # Blocking work simulation (safe in threaded executor) 
            
            # 3. Publish Feedback
            feedback_msg.distance_remaining = distance
            goal_handle.publish_feedback(feedback_msg)
            self.get_logger().info(f'Feedback: {distance}m remaining')

        # 4. Mark success and return result
        goal_handle.succeed()
        result.success = True
        result.total_time_seconds = (self.get_clock().now() - start_time).nanoseconds / 1e9
        self.get_logger().info('Goal succeeded')
        return result

def main(args=None):
    rclpy.init(args=args)
    node = NavigationActionServer()
    # MultiThreadedExecutor is often required for Action Servers 
    # to handle cancel requests while execute_callback is blocking.
    from rclpy.executors import MultiThreadedExecutor
    executor = MultiThreadedExecutor()
    rclpy.spin(node, executor=executor)
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

**Explanation**
*   **State Machine Ownership:** The server explicitly calls `goal_handle.succeed()` or `goal_handle.canceled()`. This transitions the state.
*   **Callbacks:**
    *   `goal_callback`: Decides *before* execution if the request is valid (Section 5.2 Goal Policy).
    *   `cancel_callback`: Decides if the robot *can* stop.
    *   `execute_callback`: The actual long-running loop.
*   **Feedback Loop:** Inside the loop, the server publishes `distance_remaining` every cycle, providing observability to the client.

#### Example 2: Action Client with Feedback

**Problem Statement**
A high-level planner node needs to send the robot to `(5.0, 5.0)`. It requires real-time feedback to update a UI and must be able to cancel the operation if the robot takes too long or if a user aborts the mission.

**Execution Context**
*   **File:** `mission_planner_node.py`
*   **Runtime:** Requires `nav_action_server` to be running.

**Code Block**

```python
import rclpy
from rclpy.action import ActionClient
from rclpy.node import Node
from robot_interfaces.action import NavigateToPoint

class MissionPlanner(Node):
    def __init__(self):
        super().__init__('mission_planner')
        self._action_client = ActionClient(self, NavigateToPoint, 'navigate_to_point')

    def send_goal(self, x, y):
        goal_msg = NavigateToPoint.Goal()
        goal_msg.target_x = x
        goal_msg.target_y = y

        self.get_logger().info('Waiting for action server...')
        self._action_client.wait_for_server()

        self.get_logger().info('Sending goal...')
        # Send goal and register callback for feedback
        self._send_goal_future = self._action_client.send_goal_async(
            goal_msg,
            feedback_callback=self.feedback_callback
        )
        self._send_goal_future.add_done_callback(self.goal_response_callback)

    def goal_response_callback(self, future):
        """Handle the server's acceptance or rejection of the goal."""
        goal_handle = future.result()
        if not goal_handle.accepted:
            self.get_logger().error('Goal rejected by server')
            return

        self.get_logger().info('Goal accepted. Waiting for result...')
        self._goal_handle = goal_handle # Store handle to cancel later if needed
        
        # Request the result (this future completes when action finishes)
        self._get_result_future = goal_handle.get_result_async()
        self._get_result_future.add_done_callback(self.get_result_callback)

    def feedback_callback(self, feedback_msg):
        """Called every time the server publishes feedback."""
        distance = feedback_msg.feedback.distance_remaining
        self.get_logger().info(f'>> Robot is {distance:.1f}m away...')
        
        # Example: Preempt if close enough (Cancellation logic)
        if distance < 2.0:
            self.get_logger().info('Close enough! Canceling remaining path.')
            self._action_client.cancel_goal_async(self._goal_handle)

    def get_result_callback(self, future):
        """Called when the action enters a terminal state (Success/Canceled/Aborted)."""
        result = future.result().result
        status = future.result().status
        self.get_logger().info(f'Action Finished. Status: {status}, Time: {result.total_time_seconds}s')
        rclpy.shutdown()

def main(args=None):
    rclpy.init(args=args)
    planner = MissionPlanner()
    planner.send_goal(5.0, 5.0)
    rclpy.spin(planner)

if __name__ == '__main__':
    main()
```

**Explanation**
*   **`feedback_callback`**: This function is triggered asynchronously whenever the server publishes updates. It allows the client to react (e.g., logging "Robot is 2.0m away").
*   **Preemption Logic**: Inside the feedback callback, the client evaluates `distance < 2.0`. If true, it calls `cancel_goal_async`, demonstrating the "Agency" described in Section 5.2.
*   **Goal Handle**: The client uses the `goal_handle` obtained in `goal_response_callback` to interact with this specific execution instance (Section 5.6).

## 6. Runtime Configuration with Parameters

### 6.1. The Necessity of Dynamic Configuration

In the development of robotic software, algorithmic logic often relies on numerical coefficients, boolean flags, or string identifiers that govern behavior. Examples include Proportional-Integral-Derivative (PID) gains for a motor controller, the device file path for a LIDAR sensor (e.g., `/dev/ttyUSB0`), or threshold values for obstacle detection.

Embedding these values directly into the source code ("hardcoding") creates significant engineering friction:
1.  **Compilation Overhead:** Changing a simple value requires recompiling the binary, a process that disrupts the development loop.
2.  **Reusability Limits:** A hardcoded driver cannot be reused for two identical sensors connected to different ports without code duplication.
3.  **Runtime Rigidity:** Tuning a control loop often requires adjusting values while the robot is in operation to observe immediate effects, which is impossible with compiled constants.

To resolve these issues, ROS 2 implements a **Parameter** system. This subsystem provides a standard interface for defining, effectively "injecting," and modifying configuration data at runtime, decoupling the algorithmic logic from the specific tuning values it requires.

### 6.2. The Decentralized Parameter Architecture

A critical architectural distinction in ROS 2, particularly when compared to its predecessor (ROS 1), is the **decentralization of configuration storage**.

In older frameworks, a central "Parameter Server" existed as a distinct network entity that held a global dictionary of keys and values. Nodes would query this central server to retrieve their configuration.

In ROS 2, **Parameters are owned by the individual Node**. There is no global parameter server.
*   **Node-Local Storage:** Every node maintains its own internal dictionary of parameters. The lifecycle of a parameter is bound to the lifecycle of the node that owns it. If a node terminates, its configuration data is lost from the system.
*   **Service-Based Access:** To read or write a parameter on a remote node, the system utilizes standard ROS 2 Services hidden behind the parameter client library. Every node automatically instantiates services such as `get_parameters`, `set_parameters`, and `list_parameters`.
*   **Global Events:** While storage is local, observability is global. Changes to parameters are broadcast on a dedicated `/parameter_events` topic, allowing system-level tools to monitor configuration shifts in real-time.

### 6.3. Data Typing and Primitives

ROS 2 Parameters are strictly typed. Unlike free-form dictionaries in dynamic languages (e.g., Python `dict` or JSON), a ROS 2 Parameter must hold a specific primitive data type. The underlying middleware (DDS) supports the following types:

1.  **Boolean:** Logic flags (True/False).
2.  **Integer:** 64-bit signed integers.
3.  **Double:** 64-bit floating-point numbers.
4.  **String:** UTF-8 character sequences.
5.  **Byte Array:** Binary data blobs.
6.  **Arrays:** Homogeneous lists of the above primitives (e.g., a list of doubles, but not a mixed list of integers and strings).

This strict typing enforces safety. A parameter declared as a floating-point gain cannot be accidentally overwritten with a string, preventing runtime type errors within the control logic.

### 6.4. The Declaration Contract

In ROS 2, a node cannot simply access a parameter that has not been formally **declared**. The declaration process establishes a contract between the node and the execution environment.

When a node declares a parameter, it specifies:
1.  **Name:** The string identifier (namespaced to the node).
2.  **Default Value:** A fallback value used if no external configuration is provided.
3.  **Type:** The expected data type (implicitly derived from the default value or explicitly set).
4.  **Descriptors (Optional):** Metadata constraints, such as integer ranges (e.g., $0$ to $100$) or read-only flags.

If an external launch file attempts to set a parameter that the node has not declared, the ROS 2 client library will typically reject the assignment (depending on the node's `allow_undeclared_parameters` policy, which defaults to `false`). This prevents "silent failures" where a user misspells a parameter name in a configuration file and assumes it is taking effect.

### 6.5. Dynamic Reconfiguration and Callbacks

Parameters are not merely static constants read at startup; they are mutable entities. A "Parameter Callback" mechanism allows nodes to react to external changes dynamically.

When an external agent (e.g., a CLI tool or a GUI) attempts to change a parameter via the `set_parameters` service, the owning node triggers a user-defined callback function. This function receives the proposed change and performs two actions:
1.  **Validation:** It verifies if the new value is semantically valid (e.g., ensuring a generic velocity limit is not negative).
2.  **Actuation:** If valid, it applies the change to the internal logic (e.g., updating the variable used in the main control loop).

This mechanism enables **online tuning**, allowing engineers to adjust control gains or sensor thresholds while the robot is actively performing a task, dramatically accelerating the calibration process.

### 6.6. Hierarchical Configuration Files

While parameters can be set individually via the command line, complex systems define them in **YAML** (YAML Ain't Markup Language) files. These files structure configuration hierarchically by node name.

At runtime startup (via the **Launch** system), these YAML files are parsed, and the values are pushed to the specific nodes as they initialize. This allows a single codebase to be instantiated with vastly different behaviors—for example, launching two identical camera drivers, but passing a YAML file that configures one as "Front_Camera" with high resolution and the other as "Rear_Camera" with low resolution.

### 6.7. Architectural Suitability

Parameters are the correct tool for specific data categories:

**Appropriate Use Cases:**
*   **Configuration Constants:** PID gains, max velocities, timeout durations.
*   **Hardware Identifiers:** Serial port paths, IP addresses, calibration offsets.
*   **Feature Flags:** Enabling/disabling debug logging or specific algorithm modules.

**Inappropriate Use Cases:**
*   **High-Frequency Data:** Do not use parameters to exchange sensor readings (e.g., current velocity). Use **Topics**.
*   **Large Data Blobs:** Do not use parameters to store images or large maps. Use the filesystem or specialized messages.
*   **Command Signals:** Do not use parameters to trigger actions (e.g., setting a parameter `start_moving` to true). Use **Services** or **Actions**.

### 6.8. Implementation Examples

#### Example 1: Declaration and Dynamic Reconfiguration

**Problem Statement**
A motor controller node requires a `max_speed` parameter. This value must be declared with a default for safety. Furthermore, if an engineer tries to update this value at runtime (e.g., via the CLI), the node must reject negative values (validation) and log the change (actuation).

**Execution Context**
*   **File:** `motor_controller.py`
*   **Runtime:** Run via `ros2 run` and interact via `ros2 param set`.

**Code Block**

```python
import rclpy
from rclpy.node import Node
from rclpy.exceptions import ParameterNotDeclaredException
from rclpy.parameter import Parameter
from rcl_interfaces.msg import SetParametersResult

class MotorController(Node):
    def __init__(self):
        super().__init__('motor_controller')

        # 1. Declaration: Define the contract
        # Name: 'max_speed', Default: 1.0 (float)
        self.declare_parameter('max_speed', 1.0)

        # 2. Initialization: Read the startup value
        self.current_speed_limit = self.get_parameter('max_speed').value
        self.get_logger().info(f'Motor initialized with max_speed: {self.current_speed_limit} m/s')

        # 3. Callback Registration: Handle dynamic updates
        self.add_on_set_parameters_callback(self.parameter_callback)

    def parameter_callback(self, params):
        """
        Called whenever an external agent attempts to set parameters.
        Must return SetParametersResult(successful=True/False).
        """
        for param in params:
            if param.name == 'max_speed':
                # Validation Logic
                if param.type_ != Parameter.Type.DOUBLE:
                    return SetParametersResult(successful=False, reason="max_speed must be a double")
                
                if param.value < 0.0:
                    self.get_logger().warn(f'Rejected negative speed: {param.value}')
                    return SetParametersResult(successful=False, reason="Speed cannot be negative")
                
                # Actuation Logic
                self.current_speed_limit = param.value
                self.get_logger().info(f'Dynamic update: max_speed set to {self.current_speed_limit} m/s')

        return SetParametersResult(successful=True)

def main(args=None):
    rclpy.init(args=args)
    node = MotorController()
    rclpy.spin(node)
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

**Explanation**
*   **`declare_parameter`**: Establishes the existence of `max_speed` and assigns a safe default.
*   **`add_on_set_parameters_callback`**: Hooks into the node's parameter service to intercept write requests.
*   **`SetParametersResult`**: The mechanism to accept or reject the change. If `successful=False` is returned, the Client (e.g., CLI) receives an error, and the value is *not* updated in the node.

## 8. Introspection, Diagnostics, and Visualization

### 8.1. The Observability Challenge in Distributed Robotics

In a monolithic software application, internal state can often be examined via a debugger attached to a single process memory space. However, ROS 2 systems are distributed architectures comprising distinct processes, potentially scattered across multiple computing units and communicating asynchronously. This distribution creates an **observability gap**: the internal state of the total system is not held in one location, making it opaque to the operator.

To bridge this gap, ROS 2 provides a suite of introspection subsystems. These tools allow engineers to observe the computational graph, monitor data flow, visualize geometric relationships, and record system states for post-hoc analysis. These capabilities are not merely debugging aids; they are fundamental requirements for verifying the safety and performance of autonomous machines.

### 8.2. Graph Introspection

The foundation of ROS 2 introspection is the ability to query the **Computational Graph**. As discussed in previous sections regarding the Middleware (RMW) layer, the underlying Discovery protocol maintains a distributed database of all active network participants.

Introspection tools interact with this database to reconstruct the system topology. They do not snoop on the data packets themselves but rather query the metadata regarding **Endpoints** (Publishers, Subscribers, Services, and Actions).

#### 8.2.1. The Command Line Interface (CLI) as a Probe
The primary mechanism for probing this topology is the ROS 2 Command Line Interface. The CLI acts as a transient node that joins the network, queries the discovery graph, and formats the output for the human operator.

*   **Topology Queries:** Commands such as `ros2 node list` or `ros2 topic list` interrogate the middleware to enumerate active participants and communication channels.
*   **Interface Inspection:** `ros2 interface show` retrieves the structural definition of messages or services, allowing the operator to understand the data schema without access to the source code.
*   **Data Interception:** `ros2 topic echo` instantiates a temporary subscriber. It captures serialized binary data from the wire, deserializes it using the known schema, and prints the human-readable string representation to the console. This verifies not just the existence of a link, but the successful flow of data.

### 8.3. High-Dimensional Visualization: Rviz2

While text-based introspection is sufficient for low-bandwidth data (e.g., battery voltage), robotic perception generates high-bandwidth, high-dimensional data (e.g., LiDAR point clouds, camera images, trajectory paths) that is unintelligible in text format.

**Rviz2 (ROS Visualization 2)** is the standard 3D rendering engine for the ROS ecosystem. It is critical to distinguish Rviz2 from a simulator.
*   **Simulation (e.g., Gazebo):** Generates synthetic data based on physics models.
*   **Visualization (Rviz2):** Renders actual data (whether from simulation or real hardware) onto a screen.

#### 8.3.1. The Role of Coordinate Transforms (TF)
Rviz2 operates by placing all data into a **Common Reference Frame**. A laser scan is inherently local to the sensor; a map is global to the environment. To render the laser scan correctly within the map, Rviz2 relies heavily on the **Transform (TF)** tree.

If the TF tree is broken (i.e., the geometric relationship between the sensor and the map is unknown), Rviz2 cannot render the data, regardless of whether the topic is receiving messages. Thus, Rviz2 serves as a primary validation tool for the kinematic description of the robot.

#### 8.3.2. Markers and Interactive Markers
Beyond raw sensor data, Rviz2 supports **Markers**. These are visualization primitives (cubes, arrows, text) published by nodes to communicate internal algorithmic states. For example, a motion planner might publish a "line strip" marker to visualize a planned path, or a "sphere" marker to indicate a detected obstacle center. **Interactive Markers** extend this by allowing the user to click and drag objects in the 3D scene, sending feedback to the node to update goal poses or configuration parameters.

### 8.4. Signal Analysis and Inspection: RQt

For data that is temporal rather than geometric, ROS 2 employs **RQt**. RQt is a Qt-based framework implementing a plugin architecture, allowing various graphical analysis tools to run within a single window.

#### 8.4.1. Graph Visualization
The `rqt_graph` plugin visualizes the network topology as a directed graph. Nodes are rendered as vertices, and topics are rendered as edges. This visual representation is essential for detecting "orphaned" topics (publishers with no subscribers), cyclic dependencies, or unintended disconnects in complex pipelines.

#### 8.4.2. Time-Series Plotting
The `rqt_plot` plugin functions as a digital oscilloscope for topic data. It subscribes to numerical fields within messages and renders them against time. This is indispensable for tuning control loops (e.g., visualizing the error term in a PID controller) or analyzing sensor noise characteristics.

### 8.5. System Health: The Diagnostics Subsystem

While standard logging (Info, Warn, Error) is useful for event tracking, it is unstructured and difficult for a supervisor computer to interpret automatically. The **Diagnostics** subsystem provides a standardized protocol for reporting hardware and software health.

Nodes publish formatted status reports to a simplified `/diagnostics` topic. These reports typically contain:
*   **Level:** A standardized byte (OK, WARN, ERROR, STALE).
*   **Name:** The hardware or software component ID.
*   **Message:** A human-readable description.
*   **Key-Value Pairs:** Metrics specific to the component (e.g., "CPU Temperature: 55C", "Packets Dropped: 0").

An **Aggregator** node collects these diverse reports and organizes them hierarchically, allowing a high-level executive system to make safety decisions (e.g., "Stop the robot because the LIDAR frequency is drifting").

### 8.6. Data Serialization: Rosbag2

Robotic events are often transient and irreproducible. To enable debugging and offline algorithm development, ROS 2 implements a recording mechanism known as **Rosbag2**.

Rosbag2 subscribes to specified topics and serializes the incoming messages to a storage backend (typically **SQLite3** or **MCAP**) along with their reception timestamps. This process preserves the exact binary stream of data.

#### 8.6.1. Deterministic Replay
The core utility of Rosbag2 is **Replay**. The tool can read the stored file and republish the messages onto the ROS network with the same timing characteristics as the original recording.

This allows for **Hardware-in-the-Loop (HIL)** or **Software-in-the-Loop (SIL)** testing. For example, a developer can record raw camera data during a field test, return to the lab, and replay that data into a new version of a computer vision node. The node perceives the data as live, allowing the developer to refine algorithms without needing the physical robot or the test environment.

### 8.7. Implementation Examples

#### Example 1: Publishing System Health (Diagnostics)

**Problem Statement**
A high-power motor controller needs to report its operational status to the central system supervisor. Specifically, it must report its internal temperature and input voltage. If the temperature exceeds 60°C, it should degrade the status from `OK` to `WARN`. We will implement a node that constructs and publishes standard `DiagnosticArray` messages.

**Execution Context**
*   **File:** `motor_monitor.py`
*   **Runtime:** Run via `ros2 run`. Inspect output via `ros2 topic echo /diagnostics` or the `rqt_robot_monitor` tool.

**Code Block**

```python
import random
import rclpy
from rclpy.node import Node
from diagnostic_msgs.msg import DiagnosticArray, DiagnosticStatus, KeyValue

class MotorMonitor(Node):
    def __init__(self):
        super().__init__('motor_monitor')
        # Publisher for the standard diagnostics topic
        self.diag_pub = self.create_publisher(DiagnosticArray, '/diagnostics', 1)
        
        # Check health at 1Hz
        self.timer = self.create_timer(1.0, self.publish_diagnostics)
        self.get_logger().info("Motor Monitor Initialized")

    def publish_diagnostics(self):
        # 1. Simulate Sensor Data
        temp = random.uniform(45.0, 65.0)  # Random temp between 45C and 65C
        voltage = 24.1

        # 2. Construct the Status Message (Section 8.5)
        status = DiagnosticStatus()
        status.name = "hardware_drivers: motor_controller"
        status.hardware_id = "v1.0_serial_XYZ"

        # Determine Level based on logic
        if temp < 60.0:
            status.level = DiagnosticStatus.OK
            status.message = "Nominal Operation"
        else:
            status.level = DiagnosticStatus.WARN
            status.message = "Overheating"

        # Add Metric Key-Value Pairs
        status.values = [
            KeyValue(key="Temperature (C)", value=f"{temp:.2f}"),
            KeyValue(key="Input Voltage (V)", value=f"{voltage:.2f}")
        ]

        # 3. Pack into Array (The topic expects an array of statuses)
        msg = DiagnosticArray()
        msg.header.stamp = self.get_clock().now().to_msg()
        msg.status = [status]

        self.diag_pub.publish(msg)

def main(args=None):
    rclpy.init(args=args)
    node = MotorMonitor()
    rclpy.spin(node)
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

**Explanation**
*   **`DiagnosticStatus.OK/WARN`**: We strictly adhere to the standardized byte levels defined in the message definition to ensure compatibility with Aggregators.
*   **`KeyValue`**: We convert numerical data into strings. This allows generic diagnostic tools to display the data without knowing the specific schema of a motor controller.
*   **`/diagnostics`**: By publishing to this global topic, the node automatically integrates with system-level health monitoring tools.

#### Example 2: Debugging with 3D Markers

**Problem Statement**
A perception algorithm detects the center point of an obstacle but is behaving erratically. To debug the geometric calculation, we want to visualize the detected point as a red sphere in the 3D scene (Rviz2) relative to the robot's base.

**Execution Context**
*   **File:** `obstacle_debug.py`
*   **Runtime:** Run the node, then open Rviz2 and add a "Marker" display subscribed to `/visualization_marker`.

**Code Block**

```python
import rclpy
from rclpy.node import Node
from visualization_msgs.msg import Marker

class ObstacleVisualizer(Node):
    def __init__(self):
        super().__init__('obstacle_visualizer')
        # Publisher for Rviz markers
        self.marker_pub = self.create_publisher(Marker, 'visualization_marker', 10)
        self.timer = self.create_timer(0.5, self.publish_marker)

    def publish_marker(self):
        marker = Marker()
        
        # 1. Coordinate Frame (Section 8.3.1)
        # The marker is drawn relative to the robot's base
        marker.header.frame_id = "base_link"
        marker.header.stamp = self.get_clock().now().to_msg()
        
        # 2. Identification
        marker.ns = "obstacles"
        marker.id = 0
        
        # 3. Shape and Action
        marker.type = Marker.SPHERE
        marker.action = Marker.ADD
        
        # 4. Pose (Geometric State)
        marker.pose.position.x = 2.5  # 2.5m in front of robot
        marker.pose.position.y = 0.0
        marker.pose.position.z = 0.5
        
        # 5. Scale (Dimensions in meters)
        marker.scale.x = 0.5
        marker.scale.y = 0.5
        marker.scale.z = 0.5
        
        # 6. Color (RGBA, 0.0 to 1.0)
        marker.color.r = 1.0  # Red
        marker.color.g = 0.0
        marker.color.b = 0.0
        marker.color.a = 1.0  # Alpha (1.0 = solid, 0.5 = semi-transparent)

        self.marker_pub.publish(marker)

def main(args=None):
    rclpy.init(args=args)
    node = ObstacleVisualizer()
    rclpy.spin(node)
    rclpy.shutdown()

if __name__ == '__main__':
    main()

**Explanation**
*   **`frame_id="base_link"`**: This is critical. It tells Rviz2 that the coordinates $(2.5, 0.0, 0.5)$ are relative to the robot. If the robot moves in the map, the TF tree will automatically update the position of this sphere in the global view.
*   **`Marker.ADD`**: This action tells Rviz to render the object. We could also use `DELETE` to remove it when the obstacle is cleared.
*   **`ns` (Namespace) and `id`**: These allow the node to manage multiple markers simultaneously. Publishing a new message with the same `ns` and `id` overwrites the previous one, animating the obstacle.
